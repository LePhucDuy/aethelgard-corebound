📚 Trang 1: Cẩm Nang Giải Thích Từng Cú Pháp OOP Trong Dự Án

Phân tích chuyên sâu từng cú pháp, từ khóa C++17 và nguyên lý OOP tương ứng với đề cương môn học, kèm ví dụ thực tế trích từ mã nguồn của game.

1. Đóng gói & Phạm vi truy cập

Chương 3: Class

Ẩn giấu dữ liệu nhạy cảm bên trong lớp, chỉ cho phép truy xuất có kiểm soát qua các phương thức công khai.

  • private: Chỉ có các phương thức nội bộ của lớp được truy cập. Áp dụng cho các thuộc tính sống còn như inventory, gold, poisonTimer.
  • protected: Lớp hiện tại và các lớp con kế thừa được phép truy cập. Dùng cho lớp cha Entity để các lớp con Player, Monster kế thừa chỉ số HP, ATK, DEF.
  • public: Giao diện mở cho toàn bộ chương trình tương tác (Getters, Setters, hàm cập nhật logic).
// Trích từ include/entities/Entity.h
class Entity : public IRenderable, public IDamageable {
protected:
    std::string name;
    Position pos;
    int hp, maxHp, attack, defense;
    bool alive;
public:
    int getHp() const { return hp; } // Phương thức hằng không làm đổi trạng thái
    void takeDamage(int amount) override;
};

2. Constructor & Khởi tạo Danh sách

Chương 3: Lifecycle

Khởi tạo trạng thái ban đầu của đối tượng và giải phóng tài nguyên khi hủy.

  • : var(val): Member Initializer List khởi tạo biến trực tiếp, tránh bước tạo giá trị rác rồi gán đè (tối ưu hiệu năng cao).
  • explicit: Ngăn chặn trình biên dịch tự động ép kiểu ngầm định không mong muốn khi gọi Constructor 1 tham số.
  • Copy Constructor: Sao chép sâu đối tượng, đặc biệt quan trọng với mảng động con trỏ.
// Trích từ include/core/Position.h & DynamicArray.h
struct Position {
    int x, y;
    // Member Initializer List
    Position(int x, int y) : x(x), y(y) {}
    // Copy Constructor (Sao chép tọa độ)
    Position(const Position& other) : x(other.x), y(other.y) {}
};

3. Con trỏ this & Method Chaining

Chương 3: Pointers

Con trỏ ngầm định trỏ tới chính đối tượng đang thực thi phương thức.

  • Kiểm tra tự gán: if (this != &other) trong toán tử gán, chống tự hủy dữ liệu của chính mình.
  • Method Chaining: Trả về *this dưới dạng tham chiếu Player& cho phép gọi hàm liên hoàn dạng chuỗi: hero.setHp(100).setAttack(30);
// Trích từ include/entities/Player.h
Player& setHp(int val) { hp = val; return *this; }
Player& setAttack(int val) { attack = val; return *this; }

// Sử dụng thực tế trong kiểm thử:
player.setHp(80).setAttack(25).setDefense(10);

4. Thuộc tính & Phương thức static

Chương 3: Static

Thành viên dùng chung cho toàn bộ lớp thay vì thuộc riêng về một cá thể đối tượng cụ thể.

  • static int nextInstanceId: Tự tăng khi sinh đối tượng mới, cấp phát ID duy nhất cho thực thể.
  • static int activeMonsterCount: Đếm số lượng quái vật hiện diện trên sân; tăng trong Constructor, giảm trong Destructor.
  • Khai báo trong header, nhưng bắt buộc định nghĩa vùng nhớ trong file .cpp.
// Trích từ src/core/IGameObject.cpp
int IGameObject::nextInstanceId = 0;

// Trích từ src/entities/Monster.cpp
int Monster::activeMonsterCount = 0;
int Monster::totalMonstersDefeated = 0;

5. Lớp bạn & Hàm bạn (friend)

Chương 3: Friend

Cấp quyền đặc biệt cho lớp hoặc hàm bên ngoài truy cập biến private/protected mà không cần mở public.

  • friend class CombatSystem;: Cho phép hệ thống tính sát thương truy cập trực tiếp chỉ số mà không phá vỡ tính bao bọc.
  • friend std::ostream& operator<<: Hàm bạn nạp chồng toán tử xuất stream để in thông tin đối tượng ra màn hình hoặc ghi file.
// Trích từ include/entities/Entity.h
class Entity {
    friend class CombatSystem;
    friend class SaveLoadManager;
    // Hàm bạn xuất thông tin
    friend std::ostream& operator<<(std::ostream& os, const Entity& entity) {
        os << "[" << entity.name << "] HP: " << entity.hp;
        return os;
    }
};

6. Nạp chồng toán tử toàn diện

Chương 4: Operators

Định nghĩa lại ý nghĩa của các toán tử chuẩn C++ cho các cấu trúc tùy biến.

  • Số học: operator+, operator- để cộng trừ vector vị trí.
  • 1 ngôi tiền tố & hậu tố: operator++() tăng stack bình thuốc hoặc tọa độ.
  • Chỉ số mảng: operator[] dùng trong Inventory và DynamicArray.
  • Chuyển đổi kiểu: operator Vector2() const tự động chuyển ô grid sang pixel Raylib.
// Trích từ include/core/Position.h
Position operator+(const Position& offset) const {
    return Position(x + offset.x, y + offset.y);
}
// Toán tử chuyển đổi kiểu sang Raylib Vector2
operator Vector2() const {
    return Vector2{ static_cast<float>(x * 32), static_cast<float>(y * 32) };
}

7. Kế thừa kim cương (Diamond Problem)

Chương 5: Inheritance

Giải quyết hiện tượng nhập nhằng thuộc tính khi một lớp kế thừa từ 2 lớp con có chung 1 lớp cha gốc.

  • Lớp IRenderable và IDamageable cùng kế thừa từ IGameObject.
  • Lớp Entity đa kế thừa từ cả hai giao diện trên.
  • Sử dụng cú pháp virtual public IGameObject giúp Entity chỉ sở hữu DUY NHẤT 1 bản sao của instanceId.
// Trích từ include/core/IDamageable.h & IRenderable.h
class IDamageable : virtual public IGameObject { ... };
class IRenderable : virtual public IGameObject { ... };

// Entity kế thừa đồng thời 2 giao diện
class Entity : public IRenderable, public IDamageable { ... };

8. Lớp trừu tượng & Đa hình động

Chương 6: Polymorphism

Cơ chế liên kết động (Late Binding) gọi đúng phương thức của lớp con thông qua con trỏ lớp cha lúc chạy.

  • Phương thức thuần ảo: virtual void act(...) = 0; biến lớp thành Abstract Class.
  • Từ khóa override: Yêu cầu trình biên dịch kiểm tra tính hợp lệ của hàm ghi đè ở lớp con.
  • Virtual Destructor: virtual ~Entity() = default; giải phóng bộ nhớ an toàn.
// Trích từ include/entities/Monster.h & Boar.h
class Monster : public Entity {
public:
    virtual void act(Dungeon& d, Player& p, std::vector<std::string>& log) = 0;
    virtual void onDeath(Player& player) = 0;
};

9. RTTI & Ép kiểu an toàn dynamic_cast

Chương 6: RTTI

Xác định kiểu dữ liệu thực sự của đối tượng trong thời gian chạy (Run-Time Type Information).

  • dynamic_cast<T*>(ptr): Trả về con trỏ đích nếu đối tượng đúng là kiểu con, ngược lại trả về nullptr.
  • Được dùng khi Save/Load file để phân biệt vật phẩm trong túi là Weapon hay Potion.
// Trích từ src/systems/SaveLoadManager.cpp
const Item* item = inv[i];
const Weapon* w = dynamic_cast<const Weapon*>(item);
if (w) {
    outFile << "Item=" << w->getName() << "|...|WEAPON|" << w->getBonusAttack() << "\n";
}

NHÓM 1: CÂU HỎI CƠ BẢN VỀ LỚP, ĐỐI TƯỢNG & ĐÓNG GÓI

GIẢNG VIÊN HỎI 1. Trong C++, struct và class khác nhau ở điểm nào? Tại sao em dùng struct cho Position, DamagePopup nhưng lại dùng class cho Player, Dungeon?
💡 Câu trả lời chuẩn xác:

Trong C++, điểm khác biệt duy nhất giữa struct và class là phạm vi truy cập mặc định: với struct, các thành viên mặc định là public; còn với class, các thành viên mặc định là private.

Lý do lựa chọn trong dự án:
• struct được dùng cho các cấu trúc mang tính chất thuần chứa dữ liệu (Plain Old Data / DTO) như Position (x, y), DamagePopup, GoldParticle nơi các thuộc tính thường xuyên được truy xuất trực tiếp để tính toán tọa độ đồ họa mà không cần logic bao bọc phức tạp.
• class được dùng cho Player, Monster, Dungeon, Inventory để đảm bảo Tính đóng gói (Encapsulation) nghiêm ngặt, che giấu máu, giáp, danh sách con trỏ mảng, buộc mọi tương tác phải thông qua các hàm nghiệp vụ có kiểm tra logic hợp lệ.
GIẢNG VIÊN HỎI 2. Constructor sao chép (Copy Constructor) được gọi trong những trường hợp nào? Nếu không tự viết Copy Constructor cho lớp DynamicArray thì điều gì nguy hiểm sẽ xảy ra?
💡 Câu trả lời chuẩn xác:

Copy Constructor được gọi khi:

  • Khởi tạo một đối tượng mới từ một đối tượng có sẵn: DynamicArray<int> b = a; hoặc DynamicArray<int> b(a);
  • Truyền một đối tượng vào hàm theo hình thức truyền giá trị (Pass-by-value).
  • Hàm trả về một đối tượng theo giá trị (Return-by-value).
Nguy cơ cực kỳ nghiêm trọng nếu dùng Copy Constructor mặc định:
Constructor mặc định của trình biên dịch chỉ thực hiện sao chép nông (Shallow Copy) bit-by-bit. Nó sẽ sao chép nguyên xi con trỏ data từ đối tượng cũ sang đối tượng mới, khiến cả hai đối tượng cùng trỏ vào một vùng nhớ trên Heap.
Khi một trong hai đối tượng bị hủy, hàm Destructor gọi delete[] data; giải phóng vùng nhớ đó. Khi đối tượng thứ hai bị hủy sau đó, nó tiếp tục gọi delete[] trên vùng nhớ đã bị giải phóng → Dẫn đến lỗi sập chương trình nghiêm trọng Double Free Error / Dangling Pointer và làm treo game. Do đó, trong DynamicArray, chúng em bắt buộc phải tự viết Copy Constructor để cấp phát một vùng nhớ hoàn toàn mới và sao chép từng giá trị sang (Deep Copy).
GIẢNG VIÊN HỎI 3. Từ khóa friend có vi phạm nguyên lý Đóng gói (Encapsulation) không? Tại sao em lại sử dụng friend trong Entity và Position?
💡 Câu trả lời chuẩn xác:

Về mặt lý thuyết bề mặt, friend cho phép lớp hoặc hàm bên ngoài truy cập vào các biến private/protected của lớp. Tuy nhiên, friend không vi phạm tính đóng gói nếu được sử dụng có chủ đích và kiểm soát chặt chẽ, vì quyền kết bạn do chính lớp đó tự trao quyền chứ không bị áp đặt từ bên ngoài.

Lý do sử dụng trong dự án:
1. Trong Entity, việc cấp quyền friend class CombatSystem; và friend class SaveLoadManager; giúp hai phân hệ chuyên trách tính toán giao tranh và ghi tệp tiến trình truy xuất nhanh chỉ số nội bộ mà không cần phải "mở toang" bằng cách tạo các hàm public setHp() tùy tiện cho các thành phần khác gọi bừa bãi.
2. Trong Position, toán tử xuất nhập stream operator<< và operator>> bắt buộc phải nhận đối số bên trái là std::ostream& (không thể là con trỏ this), do đó bắt buộc phải khai báo là một hàm toàn cục (global function) dạng friend để nó có thể đọc biến pos.x, pos.y.
GIẢNG VIÊN HỎI 4. Toán tử tiền tố (++pos) và hậu tố (pos++) khác nhau thế nào về cú pháp khai báo, cơ chế hoạt động và hiệu năng? Tại sao hàm hậu tố lại nhận thêm tham số int giả?
💡 Câu trả lời chuẩn xác:

Trong C++, toán tử tiền tố (Prefix) và hậu tố (Postfix) có sự khác biệt rõ rệt về cú pháp, cơ chế trả về và hiệu năng:

  • Toán tử tiền tố (++pos): Khai báo là Position& operator++(). Thực hiện tăng giá trị thuộc tính của đối tượng trước, sau đó trả về tham chiếu chính đối tượng đó (*this). Không tạo bất kỳ bản sao nào trong RAM, đạt hiệu năng tối ưu.
  • Toán tử hậu tố (pos++): Khai báo là Position operator++(int). Bắt buộc phải tạo một biến tạm lưu lại trạng thái cũ: Position temp = *this;, sau đó mới tăng giá trị nội bộ, và cuối cùng trả về biến tạm temp theo giá trị (Return-by-value).
Tại sao hàm hậu tố lại có tham số (int)?
Vì cả hai toán tử đều có cùng tên gọi là operator++. Để trình biên dịch C++ có thể phân biệt chữ ký hàm (Function Signature) khi quá tải, tiêu chuẩn C++ quy ước đưa vào một tham số giả (dummy parameter) kiểu int không có tên biến trong hàm hậu tố. Trình biên dịch sẽ tự động truyền giá trị 0 vào tham số này khi gặp cú pháp pos++.
GIẢNG VIÊN HỎI 5. Tại sao các hàm Getter như getHp(), getPosition() lại có từ khóa const ở cuối hàm? Điều gì xảy ra nếu cố tình sửa biến bên trong hàm const? Khi nào ta phải dùng từ khóa mutable?
💡 Câu trả lời chuẩn xác:

Từ khóa const đặt ở cuối hàm thành viên (int getHp() const) biến con trỏ ngầm định this thành con trỏ hằng trỏ tới đối tượng hằng (const Entity* const this):

  • Mục đích: Cam kết với trình biên dịch rằng phương thức này chỉ đọc (Read-only), tuyệt đối không làm thay đổi bất kỳ thuộc tính dữ liệu nào của đối tượng.
  • Nếu cố tình sửa biến: Trình biên dịch sẽ báo lỗi biên dịch ngay lập tức (Compile-time Error: assignment of member in read-only object).
  • Nguyên tắc const-correctness: Một đối tượng hằng (hoặc tham chiếu hằng const Entity& e) CHỈ ĐƯỢC PHÉP gọi các phương thức có gắn nhãn const. Nếu getter không có const, ta sẽ không thể đọc thông tin của đối tượng hằng khi truyền qua hàm.
Khi nào dùng từ khóa mutable?
Từ khóa mutable được khai báo trước một thuộc tính thành viên để cho phép thuộc tính đó vẫn có thể bị thay đổi giá trị ngay bên trong các hàm thành viên hằng const. Thường áp dụng cho các biến không ảnh hưởng đến trạng thái nghiệp vụ cốt lõi của đối tượng, ví dụ: biến đếm số lần truy xuất (debug counter), bộ đệm kết quả tính toán (cache), hoặc biến khóa đồng bộ đa luồng mutable std::mutex mtx;.

GIẢNG VIÊN HỎI 6. Bài toán kim cương (Diamond Problem) là gì? Trong dự án của em nó xuất hiện ở đâu và em đã dùng cú pháp gì để giải quyết triệt để?
💡 Câu trả lời chuẩn xác:

Bài toán kim cương xảy ra trong mô hình đa kế thừa (Multiple Inheritance) khi một lớp con (D) kế thừa từ hai lớp cha (B và C), mà hai lớp cha này lại cùng kế thừa từ một lớp ông bà gốc (A). Khi đó, lớp D sẽ nhận hai bản sao riêng biệt của tất cả các thuộc tính của A, dẫn đến hiện tượng xung đột lưỡng nghĩa (Ambiguity) khi truy cập thuộc tính và gây lãng phí bộ nhớ.

Xuất hiện trong dự án Aethelgard:
• Lớp gốc: IGameObject (chứa mã định danh thực thể instanceId).
• Hai lớp con: IRenderable và IDamageable.
• Lớp đáy: Entity (kế thừa cả hai giao diện trên: vừa vẽ được, vừa chịu sát thương được).

Cú pháp giải quyết:
Sử dụng Kế thừa ảo (Virtual Inheritance) bằng từ khóa virtual public IGameObject ở cả IRenderable và IDamageable.
Khi trình biên dịch tạo đối tượng Entity, nó sẽ sử dụng bảng con trỏ ảo (Virtual Base Table Pointer) để chia sẻ chung DUY NHẤT một bản sao của IGameObject. Điều này đã được kiểm chứng tuyệt đối trong hàm kiểm thử runOOPAcademicTests(): con trỏ ép kiểu từ Renderable và Damageable đều trỏ về cùng một địa chỉ IGameObject* với cùng một instanceId.
GIẢNG VIÊN HỎI 7. Tại sao hàm hủy của lớp cơ sở Entity bắt buộc phải có từ khóa virtual (~Entity())? Nếu em xóa từ khóa virtual này đi thì hậu quả gì xảy ra?
💡 Câu trả lời chuẩn xác:

Trong C++, khi ta quản lý và giải phóng một đối tượng lớp con (như BoarKing hay Player) thông qua con trỏ lớp cơ sở (Entity* hoặc std::unique_ptr<Entity>):

• Nếu hàm hủy CÓ từ khóa virtual: Trình biên dịch sẽ tra cứu Bảng phương thức ảo (vtable) lúc chạy để kích hoạt đúng hàm hủy của lớp con trước, sau đó mới gọi ngược lên hàm hủy của lớp cha theo đúng thứ tự phân rã đối tượng.
• Nếu KHÔNG CÓ virtual (bị xóa đi): Trình biên dịch sẽ áp dụng liên kết tĩnh (Static Binding) và chỉ gọi hàm hủy của Entity. Toàn bộ các thuộc tính riêng, bộ nhớ động, texture, std::map hoạt họa nằm trong các lớp con (như BoarKing, Player) sẽ hoàn toàn bị bỏ qua, không bao giờ được giải phóng → Gây ra lỗi rò rỉ bộ nhớ nghiêm trọng (Memory Leak) và là hành vi không xác định (Undefined Behavior) theo tiêu chuẩn C++.
GIẢNG VIÊN HỎI 8. Hãy phân biệt 3 mối quan hệ cơ bản trong OOP: Kế thừa (Inheritance / IS-A), Hợp thành (Composition / HAS-A mạnh) và Kết hợp (Aggregation / HAS-A yếu)? Chỉ rõ trong mã nguồn dự án.
💡 Câu trả lời chuẩn xác:

Sự khác biệt bản chất giữa 3 mối quan hệ nằm ở mức độ ràng buộc và vòng đời (Lifecycle) giữa các đối tượng:

  • 1. Kế thừa (Inheritance - quan hệ "IS-A"): Lớp dẫn xuất là một dạng cụ thể hóa của lớp cơ sở.
    Minh chứng trong dự án: Player IS-A Entity; BoarKing IS-A Monster.
  • 2. Hợp thành (Composition - quan hệ "HAS-A chặt chẽ / Part-of"): Đối tượng cha sở hữu trọn vẹn đối tượng con. Vòng đời của con gắn liền tuyệt đối với cha (cha sinh con sinh, cha chết con chết theo).
    Minh chứng trong dự án: Player sở hữu Inventory; Dungeon sở hữu ma trận Tile mapGrid[15][11]. Khi đối tượng Player hay Dungeon bị hủy thì Inventory và Tile cũng lập tức biến mất khỏi bộ nhớ.
  • 3. Kết hợp (Aggregation - quan hệ "HAS-A lỏng lẻo / Uses-a"): Đối tượng này chứa hoặc sử dụng đối tượng kia thông qua con trỏ hoặc tham chiếu, nhưng vòng đời độc lập với nhau.
    Minh chứng trong dự án: Monster kết hợp với IAIStrategy* (chiến lược AI có thể được hoán đổi hoặc chia sẻ giữa nhiều quái); Inventory chứa danh sách con trỏ Item* (vật phẩm có thể vứt ra sàn Dungeon hoặc chuyển sang rương mà không bị hủy cùng lúc).
GIẢNG VIÊN HỎI 9. C++ không có từ khóa "interface" như Java hay C#, vậy em tạo ra một Interface trong C++ bằng cách nào? Phân biệt Pure Interface và Abstract Class?
💡 Câu trả lời chuẩn xác:

Trong C++, một Interface được tạo ra dưới dạng một Lớp trừu tượng đặc biệt (Pure Abstract Class) thỏa mãn các tiêu chuẩn nghiêm ngặt sau:

  1. Tất cả các phương thức thành viên đều là phương thức thuần ảo (virtual void func() = 0;).
  2. KHÔNG CÓ bất kỳ biến thành viên dữ liệu nào (No state/data members), chỉ đóng vai trò một bản hợp đồng giao tiếp thuần túy.
  3. Bắt buộc phải có một Virtual Destructor: virtual ~Interface() = default;.
Khác biệt với Abstract Class thông thường trong dự án:
• Pure Interface: IRenderable và IDamageable chỉ chứa hàm thuần ảo render(), takeDamage(), hoàn toàn không lưu trữ biến.
• Abstract Class: Entity và Monster tuy cũng là lớp trừu tượng (không thể tạo đối tượng trực tiếp do có hàm thuần ảo act() = 0), nhưng chúng có chứa thuộc tính dữ liệu dùng chung (như hp, maxHp, attack, defense, position) và đã hiện thực sẵn các hàm cơ bản như isAlive(), heal() để các lớp con thừa hưởng mà không phải viết lại.

GIẢNG VIÊN HỎI 10. Phân biệt Liên kết tĩnh (Early Binding) và Liên kết động (Late Binding)? Trong dự án, vòng lặp cập nhật quái vật dungeon.update() thể hiện tính đa hình như thế nào?
💡 Câu trả lời chuẩn xác:

1. Liên kết tĩnh (Early / Static Binding): Trình biên dịch xác định địa chỉ hàm cần gọi ngay trong quá trình biên dịch (Compile-time). Xảy ra với hàm thông thường, hàm nạp chồng (Overloading), hoặc khi gọi qua đối tượng cụ thể trực tiếp.

2. Liên kết động (Late / Dynamic Binding): Việc gọi hàm được hoãn lại để quyết định trong thời gian chạy (Runtime) dựa vào con trỏ vtable của đối tượng thực tế. Xảy ra khi gọi phương thức virtual qua con trỏ hoặc tham chiếu lớp cơ sở.

Minh chứng trong hàm dungeon.update():
Danh sách quái vật được lưu trữ trong một vector đồng nhất: std::vector<std::unique_ptr<Monster>> monsters;.
Khi duyệt vòng lặp for (auto& m : monsters) m->act(dungeon, player, log);:
Về mặt tĩnh tại thời điểm biên dịch, trình biên dịch chỉ biết m là con trỏ kiểu cha Monster*. Nhưng tại thời điểm chạy (Runtime), chương trình tra cứu vtable và tự động gọi đúng hàm Boar::act() (lợn rừng húc), hoặc SmallBee::act() (ong bay chích độc), hoặc Snail::act() (ốc sên rút vỏ). Đây chính là đỉnh cao của Tính Đa hình (Polymorphism): cùng một lời gọi hàm nhưng sinh ra nhiều hành vi hoàn toàn khác nhau.
GIẢNG VIÊN HỎI 11. Dưới góc độ tổ chức bộ nhớ RAM, cơ chế Đa hình hoạt động ra sao? vtable và vptr được lưu ở đâu? Kích thước sizeof của một đối tượng tăng thêm bao nhiêu khi có hàm virtual?
💡 Câu trả lời chuẩn xác:

Dưới tầng sâu kiến trúc máy tính, Đa hình động trong C++ được hiện thực thông qua hai thành phần cốt lõi:

  • 1. Bảng hàm ảo (vtable - Virtual Method Table): Là một mảng tĩnh chứa các con trỏ hàm trỏ tới địa chỉ của các phương thức virtual tương ứng của từng lớp. Mỗi class có hàm virtual sẽ sở hữu duy nhất MỘT bảng vtable được trình biên dịch tạo ra trong vùng nhớ chỉ đọc (Read-only Data / Text Segment).
  • 2. Con trỏ bảng ảo (vptr - Virtual Table Pointer): Mỗi một đối tượng thực thể (instance) khi được tạo ra trong bộ nhớ (Stack hoặc Heap) sẽ được trình biên dịch tự động chèn thêm một con trỏ ẩn vptr tại ngay đầu vùng nhớ đối tượng, trỏ tới bảng vtable của lớp tương ứng.
Tác động tới kích thước bộ nhớ (sizeof) và chi phí thực thi:
• Do có thêm con trỏ vptr, kích thước sizeof của đối tượng sẽ tăng thêm đúng bằng kích thước của 1 con trỏ hệ thống: tăng đúng 8 bytes trên hệ điều hành 64-bit (hoặc 4 bytes trên 32-bit).
• Khi gọi m->act(), CPU thực hiện 3 bước: (1) Đọc con trỏ vptr từ đối tượng m → (2) Truy xuất địa chỉ hàm tại chỉ số của act() trong vtable → (3) Nhảy tới địa chỉ hàm thực thi. Quá trình tra cứu gián tiếp này chỉ mất vài chu kỳ CPU nhưng mang lại tính linh hoạt tuyệt đối cho mã nguồn.
GIẢNG VIÊN HỎI 12. Tại sao mã nguồn của Class Template (DynamicArray<T>) và Function Template (clamp<T>) bắt buộc phải viết trong file header (.h) mà không tách ra file .cpp? Cơ chế Template Instantiation diễn ra khi nào?
💡 Câu trả lời chuẩn xác:

Khác với các hàm và lớp thông thường, Template (Khuôn mẫu) không phải là mã máy thực thi (Executable Code), mà nó chỉ là một bản thiết kế mẫu (Blueprint) để trình biên dịch dựa vào đó sinh mã:

  • Cơ chế Template Instantiation (Thực thể hóa): Diễn ra hoàn toàn tại Thời điểm biên dịch (Compile-time). Khi gặp một khai báo cụ thể như DynamicArray<int> hay DynamicArray<Monster*>, trình biên dịch mới lấy kiểu cụ thể đó thay thế vào tham số loại T để sinh ra mã nhị phân thực sự.
  • Hậu quả nếu tách mã ra file .cpp: Trình biên dịch C++ biên dịch từng file .cpp độc lập (Translation Unit). Nếu ta viết phần cài đặt template trong DynamicArray.cpp, khi biên dịch file đó, trình biên dịch chưa biết kiểu T nào sẽ được dùng nên không sinh ra bất kỳ mã máy nào. Khi các file khác (như main.cpp) gọi DynamicArray<int>, trình liên kết (Linker) sẽ báo lỗi nổi tiếng: undefined reference to DynamicArray<int>::push_back(...).
Kết luận: Mã hiện thực của mọi Template trong C++ bắt buộc phải được đặt trọn vẹn trong file header (.h hoặc .hpp) để bất kỳ file mã nguồn nào include cũng có đủ thông tin để tự sinh mã tại chỗ.
GIẢNG VIÊN HỎI 13. Phân biệt static_cast và dynamic_cast trong C++? Điều kiện tiên quyết để dùng được dynamic_cast là gì và điều gì xảy ra nếu ép kiểu thất bại với con trỏ vs tham chiếu?
💡 Câu trả lời chuẩn xác:

Sự khác biệt cốt tử giữa static_cast và dynamic_cast nằm ở thời điểm kiểm tra kiểu dữ liệu:

  • static_cast (Kiểm tra tại Compile-time): Dùng để chuyển đổi giữa các kiểu dữ liệu có liên quan rõ ràng (như ép kiểu số nguyên sang số thực, ép con trỏ lớp con lên lớp cha - Upcasting). Nếu ép ngược từ lớp cha xuống lớp con (Downcasting) mà đối tượng thực tế không phải kiểu con, static_cast vẫn cho phép ép, dẫn tới con trỏ rác và làm crash game lúc chạy.
  • dynamic_cast (Kiểm tra tại Runtime bằng RTTI): Dùng để ép kiểu an toàn từ lớp cơ sở xuống lớp dẫn xuất (Downcasting). Trình biên dịch kiểm tra thông tin kiểu lúc chạy (Run-Time Type Information) xem đối tượng thực sự có phải là kiểu đích hay không.
1. Điều kiện tiên quyết: Lớp cơ sở bắt buộc phải có tính đa hình (Polymorphic Class), nghĩa là phải chứa ít nhất một phương thức virtual (chẳng hạn như Virtual Destructor) để kích hoạt bảng vtable chứa thông tin RTTI.

2. Hành vi khi ép kiểu thất bại:
• Với con trỏ (T*): Trả về con trỏ an toàn là nullptr (Ví dụ: const Weapon* w = dynamic_cast<const Weapon*>(item); if (!w) ...).
• Với tham chiếu (T&): Do C++ không có khái niệm "tham chiếu null", nên dynamic_cast sẽ lập tức ném ra ngoại lệ std::bad_cast, buộc lập trình viên phải bao quanh bằng khối try...catch.

GIẢNG VIÊN HỎI 14. Tại sao trong dự án em dùng std::unique_ptr mà không dùng con trỏ thô (raw pointer T*) hoặc std::shared_ptr để quản lý Monsters và Items?
💡 Câu trả lời chuẩn xác:

Việc lựa chọn std::unique_ptr tuân thủ nghiêm ngặt triết lý thiết kế hướng đối tượng hiện đại và nguyên lý RAII (Resource Acquisition Is Initialization):

  • So với con trỏ thô (Raw pointer): Con trỏ thô buộc lập trình viên phải nhớ gọi delete thủ công ở mọi nhánh thoát lỗi. Với std::unique_ptr, khi monsters.clear() hoặc Dungeon bị hủy, toàn bộ quái vật tự động được dọn sạch khỏi RAM 100%.
  • So với std::shared_ptr: std::shared_ptr duy trì khối điều khiển bộ đếm tham chiếu trên heap và chi phí đồng bộ luồng. Quan trọng hơn về mặt ngữ nghĩa kiến trúc: Mỗi quái vật hoặc mỗi món đồ trong hầm ngục chỉ thuộc về DUY NHẤT một chủ sở hữu độc quyền (Dungeon hoặc Inventory), đó là quan hệ Composition (Hợp thành). Do đó dùng std::unique_ptr là chuẩn xác nhất.
GIẢNG VIÊN HỎI 15. Trong phân hệ SaveLoadManager, tại sao khi bắt ngoại lệ bắt buộc phải viết catch (const GameException& e) thay vì catch (GameException e)? Giải thích hiện tượng Cắt gọt đối tượng (Object Slicing).
💡 Câu trả lời chuẩn xác:

Trong C++, việc bắt ngoại lệ bằng tham chiếu (catch (const GameException& e)) là quy tắc vàng bắt buộc của môn OOP:

  • Hiện tượng Cắt gọt đối tượng (Object Slicing) nếu bắt bằng giá trị: Nếu viết catch (GameException e), khi một lớp con như SaveLoadException hay OutOfBoundsException được ném ra, trình biên dịch sẽ chỉ sao chép phần dữ liệu của lớp cha GameException vào biến e. Toàn bộ các thuộc tính đặc thù và hàm ảo what() của lớp con sẽ bị cắt gọt vứt bỏ hoàn toàn. Hơn nữa, nó còn tốn chi phí gọi Copy Constructor vô ích.
  • Lợi ích khi bắt bằng tham chiếu hằng: Truyền tham chiếu giúp bảo toàn tính đa hình (Polymorphic Catching). Khi gọi e.what(), chương trình sẽ gọi chính xác hàm what() của lớp ngoại lệ thực tế được ném ra, in ra thông báo lỗi chi tiết chính xác của từng trường hợp tệp hỏng.
GIẢNG VIÊN HỎI 16. Hệ thống Thành tựu (Achievement System) của em hoạt động như thế nào? Tại sao em dùng Observer Pattern thay vì gọi trực tiếp hàm mở khóa trong CombatSystem?
💡 Câu trả lời chuẩn xác:

Hệ thống Thành tựu trong game được thiết kế theo Mẫu thiết kế Quan sát (Observer Pattern) gồm 3 thành phần:

  • Subject (Bộ phát tán): Lớp Singleton EventDispatcher quản lý danh sách người đăng ký theo từng loại sự kiện.
  • Observer Interface: Giao diện thuần ảo IGameObserver với phương thức hợp đồng onNotify(const GameEvent& event) = 0.
  • Concrete Observer: AchievementObserver lắng nghe các sự kiện như MONSTER_KILLED, BOSS_DEFEATED, GOLD_GAINED.
Lý do thiết kế tối thượng (Decoupling):
Với Observer Pattern, CombatSystem chỉ việc làm đúng nhiệm vụ chiến đấu và "bắn" ra một thông báo EventDispatcher::getInstance().notify(event) mà không cần quan tâm ai đang nghe. GIẢNG VIÊN HỎI 18. Em hãy chỉ ra ít nhất 3 nguyên lý trong bộ nguyên lý SOLID mà dự án Aethelgard đã áp dụng thành công?
💡 Câu trả lời chuẩn xác:

Dự án tuân thủ chặt chẽ các nguyên lý thiết kế hướng đối tượng chuẩn công nghiệp SOLID:

  • S - Single Responsibility Principle (Đơn trách nhiệm): Mỗi lớp chỉ giữ một trách nhiệm duy nhất. Lớp Entity chỉ chứa trạng thái sinh mệnh và hiển thị, tuyệt đối không kiêm nhiệm việc tính sát thương hay đọc tệp. Toàn bộ logic giao tranh được giao cho CombatSystem, việc nạp tệp giao cho SaveLoadManager.
  • O - Open/Closed Principle (Mở để mở rộng, Đóng để sửa đổi): Hệ thống cho phép bổ sung thêm quái mới (như Goblin), kỹ năng mới (như ThunderSlash) bằng cách tạo lớp kế thừa mới từ Monster và Skill mà không cần sửa đổi một dòng code nào trong vòng lặp chính của GameEngine hay Dungeon.
  • D - Dependency Inversion Principle (Đảo ngược phụ thuộc): Các module cấp cao (như Monster hay GameEngine) không phụ thuộc trực tiếp vào các module cấp thấp cụ thể, mà phụ thuộc vào các giao diện trừu tượng như IAIStrategy và IGameObserver.

CƠ BẢN 2 2. "Kế thừa kim cương (Diamond Problem) phát sinh ở đâu trong dự án và tại sao phải dùng virtual public IGameObject?"
💡 Đáp án mẫu cho Duy:

Dạ, hiện tượng kim cương phát sinh khi lớp cha gốc IGameObject (chứa mã định danh instanceId) được kế thừa bởi hai giao diện là IRenderable (giao diện vẽ) và IDamageable (giao diện nhận sát thương). Sau đó lớp Entity lại đa kế thừa từ cả hai giao diện này. Nếu không dùng kế thừa ảo, Entity sẽ chứa hai bản sao độc lập của IGameObject dẫn tới lỗi nhập nhằng (ambiguity) khi truy cập. Khi khai báo virtual public IGameObject ở cả hai lớp con trung gian, trình biên dịch C++ tạo bảng con trỏ ảo vbptr và đảm bảo trong bộ nhớ của Entity chỉ tồn tại duy nhất 1 vùng nhớ chung cho IGameObject, giải quyết triệt để lỗi kim cương.

CƠ BẢN 3 3. "Lớp Skill được quản lý trong Player như thế nào? Cơ chế tính thời gian hồi chiêu (Cooldown) và tiêu hao Mana được thiết kế ra sao?"
💡 Đáp án mẫu cho Duy:

Mỗi đối tượng Skill đóng gói đầy đủ: tên chiêu, lượng mana tiêu hao (manaCost), thời gian hồi chiêu tối đa (maxCooldown) và bộ đếm thời gian hồi hiện tại (currentCooldown).
Khi người chơi bấm phím thi triển (phím [J] Chém quét Slash, phím [L] Lướt né Dash):
1. Player kiểm tra điều kiện: if (currentMana >= skill.getManaCost() && skill.isReady()).
2. Nếu thỏa mãn, Player trừ năng lượng: currentMana -= skill.getManaCost(), kích hoạt hiệu ứng chiêu và đặt lại currentCooldown = maxCooldown.
3. Trong hàm Player::update(float deltaTime), hệ thống tự động trừ lùi currentCooldown -= deltaTime cho tới khi về 0. Thiết kế này giúp toàn bộ logic chiêu thức được đóng gói độc lập trong lớp Skill, giúp code của Player luôn sáng sủa và dễ bảo trì.

CƠ BẢN 4 4. "Mẫu thiết kế Observer Pattern trong EventSystem phân tách trách nhiệm giữa các đối tượng như thế nào?"

TÌNH HUỐNG 2 6. "Tại sao đối với túi đồ Inventory, em lại chọn quan hệ Hợp thành (Composition) trong lớp Player thay vì cho Player kế thừa (Inheritance) từ Inventory?"

TÌNH HUỐNG 4 8. "Khi game chạy trên máy yếu bị tụt FPS từ 60 xuống 20, cơ chế nhảy Parabol và LERP tọa độ của Player có bị giật hình hoặc nhảy xuyên tường không?"

CƠ BẢN 2 2. "Tại sao phương thức act() trong lớp Monster phải khai báo là thuần ảo (= 0)? Nếu em không override act() ở lớp Boar thì chuyện gì xảy ra?"

Dạ, vì Monster là một khái niệm chung chung, ta không thể biết một "con quái trừu tượng" sẽ hành động như thế nào (bay, húc hay phòng thủ), nên act() bắt buộc phải là thuần ảo virtual void act(...) = 0; để biến Monster thành Abstract Class. Nếu lớp con Boar quên không override hàm act(), thì Boar vẫn sẽ bị xem là một lớp trừu tượng và trình biên dịch sẽ báo lỗi ngay lập tức khi ta cố tình tạo đối tượng new Boar(...).

CƠ BẢN 3 3. "Bảng phương thức ảo (vtable) và con trỏ vptr hoạt động như thế nào khi gọi m->act() trong vòng lặp Dungeon::update()?"
💡 Đáp án mẫu cho Thiện:

Dạ, mỗi khi một lớp có phương thức virtual, trình biên dịch C++ sẽ tự động sinh ra một **Bảng phương thức ảo (Virtual Table - vtable)** chứa địa chỉ các hàm ảo tương ứng của lớp đó. Trong mỗi đối tượng (như Boar hay SmallBee) sẽ có một con trỏ ẩn vptr trỏ tới vtable của lớp nó. Khi vòng lặp gọi m->act() qua con trỏ Monster*:
- Chương trình không gọi hàm tĩnh tại compile-time mà thực hiện **Liên kết muộn (Late Binding)**: truy xuất m->vptr để mở vtable, rồi nhảy đến địa chỉ hàm act() cụ thể của đối tượng thực sự trong bộ nhớ.

CƠ BẢN 4 4. "Biến tĩnh activeMonsterCount và totalMonstersDefeated trong lớp Monster có ý nghĩa gì? Tại sao phải khởi tạo ngoài file .cpp?"
💡 Đáp án mẫu cho Thiện:

Phải khởi tạo ngoài file Monster.cpp vì biến tĩnh chỉ được cấp phát 1 vùng nhớ duy nhất trong phân vùng Static Data Segment; nếu viết khởi tạo trong file .h sẽ gây lỗi đa định nghĩa (Multiple Definition Error) khi có nhiều file include.

- Trong GroundMonster::tryStepTo(), trước khi bước đi, quái vật gọi phương thức isGrounded(dungeon, nextPos) kiểm tra ô dưới chân (nextPos.x, nextPos.y + 1). Nếu ô dưới chân là EMPTY (không khí / hố vực), hàm trả về false và quái bộ lập tức quay đầu tuần tra ngược lại, không bao giờ bị rơi.
- Ngược lại, FlyingMonster ghi đè thuộc tính flying = true và lambda canFlyTo chỉ kiểm tra ô đích có phải là EMPTY không có tường cản, cho phép ong bay tự do lơ lửng trên không trung và vượt qua mọi hố vực.

TÌNH HUỐNG 3 7. "Khi ốc sên Snail bị đánh máu dưới 50%, nó rút vào vỏ (isShelled = true). Hàm takeDamage() xử lý thế nào để đòn đánh thường không gây sát thương?"

- Khi máu ban đầu tụt xuống dưới 50% MaxHP, ốc sên tự động bật cờ isShelled = true và kích hoạt bộ đếm thời gian shellTimer = 3.0f để phòng thủ trong 3 giây trước khi thò đầu ra tấn công tiếp.

TÌNH HUỐNG 4 8. "Nếu muốn thêm một loài quái mới biết tàng hình (Ghost), Thiện sẽ kế thừa từ lớp nào và override những hàm nào mà không phá vỡ code cũ?"
💡 Đáp án mẫu cho Thiện:

Dạ, tuân theo nguyên lý **Đóng/Mở (Open/Closed Principle)**, em sẽ làm như sau:
1. Tạo lớp Ghost kế thừa từ FlyingMonster (vì bóng ma biết bay lơ lửng).
2. Thêm thuộc tính bool isInvisible = true; và bộ đếm thời gian hiện hình.
3. Override hàm thuần ảo act(): khi ở xa người chơi thì tàng hình, khi áp sát trong cự ly 2 ô thì hiện hình tung đòn ám sát.
4. Override hàm render(): khi đang tàng hình thì vẽ với độ trong suốt alpha thấp hoặc ẩn hình ảnh.
Toàn bộ lớp Dungeon, GameEngine và các quái vật khác hoàn toàn không phải sửa đổi một dòng nào!

TÌNH HUỐNG 5 9. "Nếu tệp savegame.dat bị ai đó mở Notepad chỉnh sửa sai định dạng, dữ liệu quái vật âm hoặc bị rỗng thì SaveLoadManager của em xử lý thế nào?"
💡 Đáp án mẫu cho Thiện:

Dạ thưa thầy, trong SaveLoadManager::loadGame(), em thiết kế cơ chế tự vệ và bẫy lỗi đa tầng:
1. Kiểm tra chữ ký định danh tệp (File Header Check): Dòng đầu tiên của tệp bắt buộc phải là chuỗi nhận diện [AETHELGARD_SAVE_V1]. Nếu người dùng xóa hoặc gõ sai, hệ thống lập tức throw SaveLoadException("File save khong hop le hoac sai dinh dang!").
2. Kiểm tra tính hợp lệ của dữ liệu (Data Validation): Khi đọc chỉ số máu HP của quái, số tầng Dungeon hoặc tọa độ quái vật, nếu phát hiện số âm bất thường hoặc con trỏ đọc tệp gặp lỗi (file.fail()), hệ thống ném ngoại lệ SaveLoadException.
3. Thu dọn an toàn RAII: Vì dùng std::ifstream file(...), khi ngoại lệ bị ném ra ngoài, cơ chế Stack Unwinding của C++ sẽ tự động gọi Destructor của std::ifstream để đóng file an toàn, không làm rò rỉ File Descriptor của hệ điều hành. Sau đó thông báo lỗi được hiển thị lên màn hình để người chơi bắt đầu ván mới an toàn mà không làm sập game.

❓ Bộ Câu Hỏi Vấn Đáp Giảng Viên Dành Riêng Cho Truyền & Đáp Án Mẫu

📌 NHÓM 1: CÂU HỎI KIẾN THỨC CƠ BẢN OOP
CƠ BẢN 1 1. "Tại sao lớp Item lại là Abstract Class? Trong Inventory em lưu trữ Item* hay lưu trực tiếp đối tượng Item? Hiện tượng Object Slicing là gì?"
💡 Đáp án mẫu cho Truyền:

Dạ thưa thầy, Item là Abstract Class vì nó đại diện cho khái niệm vật phẩm trừu tượng, mỗi loại đồ cụ thể (Vũ khí, Bình thuốc, Giáp) có cách sử dụng và chỉ số cộng khác nhau nên hàm use() bắt buộc phải để thuần ảo. Trong Inventory, em bắt buộc phải lưu danh sách con trỏ std::vector<Item*> (hoặc std::unique_ptr<Item>) để áp dụng tính đa hình. Nếu lưu trực tiếp đối tượng Item theo giá trị, C++ sẽ gây ra hiện tượng Cắt gọt đối tượng (Object Slicing): trình biên dịch chỉ sao chép phần dữ liệu của lớp cha Item và cắt bỏ toàn bộ phần biến mở rộng của lớp con (làm mất sạch chỉ số tấn công của Weapon hay phòng thủ của Armor).

CƠ BẢN 2 2. "Phân biệt sự khác nhau giữa quan hệ Hợp thành (Composition) và Kết hợp (Aggregation) trong hệ thống túi đồ?"
💡 Đáp án mẫu cho Truyền:

Dạ, đây là hai mức độ của quan hệ 'HAS-A' (Sở hữu):
- Quan hệ Hợp thành (Composition): Vòng đời của thành phần phụ thuộc hoàn toàn vào đối tượng chứa. Ví dụ: Player sở hữu Inventory. Khi người chơi bị hủy, túi đồ cũng bị tiêu hủy theo.
- Quan hệ Kết hợp (Aggregation): Vòng đời của thành phần độc lập với đối tượng chứa. Ví dụ: Inventory chứa các con trỏ Item*. Khi một món đồ bị vứt ra ngoài thế giới (Drop Item) hoặc lấy ra khỏi túi để chuyển vào Rương Chest, món đồ đó vẫn tiếp tục tồn tại trên mặt đất chứ không bị giải phóng bộ nhớ ngay lập tức.

CƠ BẢN 3 3. "Toán tử dynamic_cast dùng để làm gì? Điều kiện tiên quyết để một lớp sử dụng được dynamic_cast là gì?"
💡 Đáp án mẫu cho Truyền:

Dạ, dynamic_cast là toán tử ép kiểu an toàn thời gian chạy (RTTI - Run-Time Type Information) trong C++. Em sử dụng để ép kiểu con trỏ lớp cha Item* xuống lớp con cụ thể: const Weapon* w = dynamic_cast<const Weapon*>(item);. Nếu con trỏ trỏ đúng đến một đối tượng Weapon, phép ép kiểu thành công và trả về con trỏ hợp lệ; nếu trỏ đến Potion hay Armor, nó trả về nullptr an toàn.
Điều kiện tiên quyết: Lớp cha (ở đây là Item) bắt buộc phải là Polymorphic Class (Lớp đa hình), tức phải có ít nhất một phương thức ảo (thường là virtual ~Item() = default;) để trình biên dịch tạo bảng vtable lưu thông tin RTTI.

CƠ BẢN 4 4. "Toán tử ++ và -- trong lớp Potion được cài đặt như thế nào? Cú pháp tiền tố và hậu tố khác nhau ở điểm nào?"
💡 Đáp án mẫu cho Truyền:

Dạ, trong lớp Potion, em quá tải toán tử 1 ngôi tiền tố:
Potion& operator++() { ++stackCount; return *this; }
Toán tử này tăng số lượng bình thuốc dồn trong 1 ô túi đồ lên 1 và trả về tham chiếu *this để tiếp tục thao tác.
Điểm khác biệt giữa tiền tố và hậu tố: Tiền tố operator++() không có tham số; còn hậu tố operator++(int) có thêm một tham số hình thức kiểu int giả định (dummy parameter) để trình biên dịch phân biệt cú pháp. Bản hậu tố phải tạo bản sao tạm thời nên tốn bộ nhớ hơn, vì vậy em ưu tiên dùng bản tiền tố tối ưu hiệu năng.

⚡ NHÓM 2: CÂU HỎI TÌNH HUỐNG & XỬ LÝ SỰ CỐ TRONG GAME
TÌNH HUỐNG 1 5. "Khi người chơi nhặt một bình máu mới trong khi túi đồ đã đầy 12 ô, hệ thống của em xử lý thế nào?"
💡 Đáp án mẫu cho Truyền:

Dạ thưa thầy, hàm Inventory::addItem(Item* item) xử lý tình huống này rất thông minh theo 2 bước:
1. Kiểm tra khả năng xếp chồng (Stacking Check): Nếu món đồ nhặt là một Potion, hệ thống sẽ duyệt qua 12 ô túi đồ hiện có xem đã có bình thuốc cùng ID hay chưa. Nếu đã có và chưa đạt giới hạn stack (ví dụ tối đa 10 bình), hàm sẽ gọi ++(*existingPotion) để tăng số lượng lên mà không chiếm thêm ô trống nào!
2. Nếu là trang bị mới (Weapon/Armor) hoặc bình thuốc đã đầy stack: Lúc này hệ thống kiểm tra items.size() >= maxSlots (12). Hàm trả về false, in thông báo '[TUI DO DAY!] Khong the nhat them vat pham!' và món đồ vẫn nằm an toàn trên mặt đất để người chơi dọn túi rồi nhặt lại.

TÌNH HUỐNG 2 6. "Tại sao em dùng dynamic_cast mà không dùng static_cast khi ép kiểu từ Item* sang Weapon*?"
💡 Đáp án mẫu cho Truyền:

Dạ, vì trong túi đồ chứa lẫn lộn nhiều loại con trỏ: Vũ khí (Weapon), Áo giáp (Armor), Bình thuốc (Potion).
- static_cast<Weapon*>(item) chỉ kiểm tra kiểu tại thời điểm biên dịch dựa trên quan hệ kế thừa. Lúc chạy game, nếu người chơi bấm trang bị một bình thuốc mà dùng static_cast ép sang Weapon*, trình biên dịch vẫn cho phép! Nhưng con trỏ kết quả sẽ truy cập sai vùng nhớ của Potion coi như chỉ số tấn công, dẫn tới chỉ số rác hoặc làm chương trình bị Segmentation Fault (Crash game).
- Trong khi đó, dynamic_cast kiểm tra kiểu thực tế của đối tượng tại Runtime. Nếu ép nhầm Potion sang Weapon, nó trả về nullptr, giúp em kiểm tra if (w != nullptr) an toàn tuyệt đối 100%.

TÌNH HUỐNG 3 7. "Khi nhân vật đang cầm vũ khí A (+15 ATK) mà trang bị vũ khí B (+25 ATK), việc cập nhật chỉ số ATK của Player diễn ra theo trình tự nào để không bị lỗi cộng dồn vĩnh viễn?"
💡 Đáp án mẫu cho Truyền:

Dạ, trong Inventory::equipWeapon(Player& player, int slot), em thực hiện chuẩn theo 3 bước an toàn:
1. Tháo gỡ vũ khí cũ: Nếu người chơi đang cầm vũ khí A (ví dụ biến equippedWeapon != nullptr), em trừ đi lượng bonus cũ của A: player.setAttack(player.getAttack() - equippedWeapon->getBonusAttack()).
2. Gán vũ khí mới: Cập nhật con trỏ equippedWeapon = newWeapon.
3. Cộng dồn chỉ số mới: Thêm chỉ số của vũ khí B: player.setAttack(player.getAttack() + newWeapon->getBonusAttack()).
Trình tự 'Trừ chỉ số cũ trước → Lưu trang bị mới → Cộng chỉ số mới' đảm bảo chỉ số sức mạnh của nhân vật luôn phản ánh chính xác trang bị đang mặc, không bao giờ bị bug cộng dồn vĩnh viễn.

TÌNH HUỐNG 4 8. "Khi người chơi vứt một món đồ khỏi túi (Drop item) hoặc khi tắt game, việc giải phóng vùng nhớ con trỏ Item* được đảm bảo ra sao để không bị Memory Leak?"
💡 Đáp án mẫu cho Truyền:

Dạ, trong Inventory::~Inventory(), hàm Destructor duyệt qua mảng items và gọi delete item; cho từng phần tử rồi items.clear();.
Điểm then chốt là trong lớp cơ sở Item, em đã khai báo **Virtual Destructor: virtual ~Item() = default;**. Nhờ có hàm hủy ảo, khi ta gọi delete item qua con trỏ lớp cha Item*, C++ sẽ kích hoạt Destructor của lớp con cụ thể (như ~Weapon(), ~Armor()) trước, sau đó mới giải phóng lớp cha Item, đảm bảo toàn bộ tài nguyên động của lớp con được dọn dẹp sạch sẽ 100%.

TÌNH HUỐNG 5 9. "Tại sao em áp dụng mẫu thiết kế Meyers' Singleton cho AudioSystem? Thuật toán DSP tự sinh âm thanh trong RAM hoạt động ra sao mà không cần file MP3/WAV ngoài?"
💡 Đáp án mẫu cho Truyền:

Dạ thưa thầy, em chọn Meyers' Singleton cho AudioSystem vì:
1. Tính duy nhất và an toàn luồng: Toàn bộ trò chơi chỉ được phép có duy nhất 1 thiết bị âm thanh giao tiếp với Raylib. Trong AudioSystem::getInstance(), em dùng biến cục bộ tĩnh static AudioSystem instance; return instance;. Theo chuẩn C++11/C++17 (Magic Statics), biến tĩnh cục bộ được khởi tạo an toàn luồng (Thread-safe) mà không cần dùng Mutex. Khi tắt game, Destructor tự động dọn dẹp bộ nhớ RAM.
2. Tổng hợp âm thanh thủ tục (Procedural Audio DSP): Thay vì phải nạp các file âm thanh ngoài nặng nề, em dùng thuật toán toán học tạo mảng byte sóng âm trực tiếp trong RAM: dùng hàm điều chế tần số (Frequency Sweep) cho tiếng 'keng' kim loại khi đeo kiếm và nhiễu trắng (White Noise) cho tiếng uống thuốc, giúp game độc lập và không bao giờ bị lỗi thiếu file âm thanh.

🧠 Logic Nghiệp Vụ Cốt Lõi Phụ Trách (Giải Thích Từng Bước Dễ Hiểu)

  • Xương sống tọa độ của trò chơi (Position): Game được thiết kế dưới dạng bàn cờ lưới 2D (Grid). Mọi thực thể trong game (Hiệp sĩ Player, Quái vật Monster, Rương đồ Chest, từng viên gạch Tile) đều cần biết mình đang đứng ở cột x và hàng y nào. Cấu trúc Position cung cấp phép toán cộng trừ để nhân vật bước đi (ví dụ: bấm sang phải thì pos + Position(1, 0)).
  • Cầu nối đồ họa Raylib (Operator Vector2): Máy tính vẽ hình ảnh bằng pixel, còn logic game lưu bằng ô lưới nguyên (Grid 0, 1, 2...). Toán tử ép kiểu operator Vector2() const tự động làm phép nhân: Vector2{ x * 32.0f, y * 32.0f }. Mỗi khi thư viện Raylib cần vẽ, nó tự động gọi hàm này mà lập trình viên không phải viết lại phép nhân thủ công.
  • Cơ chế hiệu ứng địa hình (Tile System): Bản đồ gồm nhiều loại ô khác nhau. Phương thức isSolid() cho biết ô đó có đi xuyên qua được không (Tường WALL thì chặn lại, Đất FLOOR thì cho đi). Phương thức getSpeedModifier() trả về hệ số tốc độ: ô thường trả về 1.0f, khi bước vào ô Đầm lầy (SWAMP) thì trả về 0.5f làm nhân vật bị dính bùn và đi chậm lại một nửa.
  • Bộ phòng thủ Ngoại lệ (Exception Safety): Để trò chơi không bị treo đột ngột (Crash) khi người chơi bước ra ngoài biên bản đồ hoặc truy cập ô không hợp lệ, hàm kiểm tra sẽ throw OutOfBoundsException(...). Hệ thống đón bắt bằng khối catch để đưa nhân vật về vị trí an toàn.
  • Hạ tầng Khuôn mẫu hàm dùng chung (CoreTemplates): Cung cấp 8 công cụ tính toán tổng quát: kẹp ngưỡng máu và tọa độ (clampValue), tìm giá trị lớn/nhỏ (getMaxValue, getMinValue), kiểm tra khoảng cách an toàn (isInRange), làm mượt đồ họa (lerpValue), và tính cự ly giữa quái và người chơi (calculateChebyshevDistance).

🎓 Kiến Thức OOP Trọng Tâm Cần Báo Cáo

  • Phân biệt struct và class (Chương 3): Giải thích lưu loát tại sao chọn struct cho Position (Plain Old Data, dữ liệu thuần, mặc định public) và class cho Tile (cần đóng gói Encapsulation, bảo vệ dữ liệu nội bộ).
  • Quá tải toán tử toàn diện (Operator Overloading - Chương 4): Nắm chắc toán tử 2 ngôi số học +, -, toán tử so sánh bằng ==, !=, toán tử tiền tố ++, và đặc biệt là toán tử chuyển đổi kiểu do người dùng tự định nghĩa operator Vector2().
  • Kế thừa ngoại lệ từ C++ Standard Library (Chương 6): Hiểu rõ cách kế thừa public std::exception, cú pháp ghi đè virtual const char* what() const noexcept override và ý nghĩa cam kết không ném lỗi của từ khóa noexcept.
  • Lập trình tổng quát với Function Templates (Chương 7 Slide 4-13): Hiểu rõ khái niệm Generic Programming, cơ chế biên dịch Template Instantiation tại Compile-time, và cách viết hàm mẫu nhận nhiều kiểu tham số độc lập template <typename T1, typename T2>.

❓ Bộ Câu Hỏi Vấn Đáp Giảng Viên Dành Riêng Cho Vinh & Đáp Án Mẫu

📌 NHÓM 1: CÂU HỎI KIẾN THỨC CƠ BẢN OOP (DỄ NHỚ - ĐÚNG TRỌNG TÂM)
CƠ BẢN 1 1. "Trong C++, struct và class khác nhau như thế nào? Tại sao em dùng struct cho Position nhưng lại dùng class cho Tile?"
💡 Đáp án mẫu cho Vinh:

Dạ thưa thầy, điểm khác biệt duy nhất giữa struct và class trong C++ là **phạm vi truy cập mặc định**:
- Trong struct, các thành viên mặc định là public.
- Trong class, các thành viên mặc định là private.
Em chọn struct cho Position vì nó là một cấu trúc dữ liệu thuần túy (Plain Old Data) gồm 2 biến tọa độ x, y thường xuyên được truy xuất trực tiếp để tính toán vị trí đồ họa. Còn Tile em dùng class vì nó cần tính đóng gói (Encapsulation) để che giấu thuộc tính loại ô tileType và bảo vệ dữ liệu, chỉ cho phép bên ngoài tương tác qua các hàm nghiệp vụ như isSolid() hay getSpeedModifier().

CƠ BẢN 2 2. "Toán tử ép kiểu operator Vector2() const trong lớp Position hoạt động như thế nào?"
💡 Đáp án mẫu cho Vinh:

Dạ, đây là Toán tử chuyển đổi kiểu do người dùng tự định nghĩa (User-defined Conversion Operator).
- Cú pháp: operator Vector2() const { return Vector2{ (float)(x * 32), (float)(y * 32) }; }
- Ý nghĩa: Trong game, logic nhân vật lưu vị trí theo ô nguyên x, y trên bàn cờ. Nhưng thư viện đồ họa Raylib lại yêu cầu kiểu tọa độ pixel thực Vector2 để vẽ lên màn hình. Nhờ có toán tử này, bất cứ khi nào em truyền một đối tượng Position vào hàm vẽ của Raylib, trình biên dịch C++ sẽ **tự động ép kiểu ngầm định sang Vector2** và nhân với 32 pixel mà không cần phải gọi hàm chuyển đổi thủ công, giúp code cực kỳ trực quan và trong sáng.

CƠ BẢN 3 3. "Lớp GameException của em kế thừa từ đâu? Từ khóa noexcept và override trong phương thức what() có tác dụng gì?"
💡 Đáp án mẫu cho Vinh:

Dạ, lớp GameException của em kế thừa từ lớp chuẩn std::exception của C++. Phương thức báo lỗi được viết như sau:
virtual const char* what() const noexcept override;
- override: Giúp trình biên dịch kiểm tra chặt chẽ xem ta có đang ghi đè chính xác hàm what() của lớp cha std::exception hay không, tránh lỗi gõ sai tên hàm.
- noexcept: Là một lời cam kết với trình biên dịch rằng hàm what() này **tuyệt đối không bao giờ phát sinh thêm bất kỳ ngoại lệ nào khác** trong quá trình đang báo lỗi, giúp chương trình xử lý an toàn và không bị gọi hàm std::terminate() làm sập ứng dụng.

CƠ BẢN 4 4. "Khuôn mẫu hàm (Function Template) là gì? Cơ chế Template Instantiation (Thực thể hóa) diễn ra khi nào?"
💡 Đáp án mẫu cho Vinh:

Dạ thưa thầy, Function Template là công cụ của lập trình tổng quát (Generic Programming). Nó cho phép lập trình viên viết một hàm mẫu duy nhất với kiểu dữ liệu hình thức T (như clampValue<T>, swapValues<T>) để tái sử dụng cho mọi kiểu dữ liệu (số nguyên int, số thực float, double) mà không phải viết lại nhiều hàm trùng lặp.
- Cơ chế Template Instantiation (Thực thể hóa): Diễn ra hoàn toàn tại **thời điểm biên dịch (Compile-time)**. Bản thân template không phải là mã nhị phân thực thi, mà chỉ là bản thiết kế mẫu (Blueprint). Khi trình biên dịch gặp lời gọi clampValue(hp, 0, 100) với tham số là int, nó mới tự động sinh ra mã máy chuyên biệt cho kiểu int.

CƠ BẢN 5 5. "Khuôn mẫu hàm calculateChebyshevDistance<T1, T2> có 2 tham số hình thức kiểu T1, T2 khác nhau hoạt động như thế nào?"
💡 Đáp án mẫu cho Vinh:

Dạ, đây là khuôn mẫu hàm nâng cao với **nhiều tham số kiểu dữ liệu độc lập** (minh họa Slide 11 Chương 7):
template <typename T1, typename T2>
int calculateChebyshevDistance(const T1& obj1, const T2& obj2) { ... }
Hàm này không quan tâm obj1 và obj2 là lớp gì, miễn là cả hai đối tượng đều có phương thức .getPosition(). Khi tính toán, em có thể truyền obj1 là một con Boss (lớp BoarKing) và obj2 là người chơi (lớp Player). Trình biên dịch sẽ tự động gán T1 = BoarKing và T2 = Player, lấy tọa độ của hai thực thể và tính khoảng cách bàn cờ cực kỳ linh hoạt mà không cần ép kiểu con trỏ.

⚡ NHÓM 2: CÂU HỎI TÌNH HUỐNG & XỬ LÝ SỰ CỐ TRONG GAME (SÁT THỰC TẾ)
TÌNH HUỐNG 1 6. "Khi nhân vật người chơi bước vào ô Đầm lầy (Swamp Tile), lớp Tile của em làm thế nào để làm người chơi bị chậm tốc độ di chuyển đi 50%?"
💡 Đáp án mẫu cho Vinh:

Dạ thưa thầy, trong lớp Tile, em thiết kế phương thức ảo:
virtual float getSpeedModifier() const { return 1.0f; }
Ở các ô gạch thông thường hoặc sàn cỏ, hàm trả về 1.0f (giữ nguyên 100% tốc độ). Nhưng ở lớp con SwampTile (ô Đầm lầy), em ghi đè hàm này và trả về 0.5f.
Khi nhân vật di chuyển trên bản đồ, hệ thống lấy ô dưới chân nhân vật và nhân tốc độ di chuyển với hệ số này: moveSpeed = baseSpeed * tile.getSpeedModifier();. Nhờ đó, nhân vật lập tức bị giảm một nửa tốc độ, tạo cảm giác di chuyển nặng nề trong bùn lầy một cách tự nhiên.

TÌNH HUỐNG 2 7. "Nếu người chơi hoặc quái vật cố tình di chuyển ra ngoài rìa bản đồ (ví dụ tọa độ x = -1 hoặc x = 200), hàm của em phát hiện và ném ngoại lệ OutOfBoundsException ra sao?"
💡 Đáp án mẫu cho Vinh:

Dạ, trong hàm kiểm tra tọa độ hợp lệ Dungeon::isValidPos(const Position& pos):
- Em kiểm tra điều kiện biên: if (pos.x < 0 || pos.x >= MAP_WIDTH || pos.y < 0 || pos.y >= MAP_HEIGHT).
- Nếu vi phạm, thay vì để chương trình truy cập vào vùng nhớ ngoài mảng gây sập game (Crash), hệ thống lập tức throw OutOfBoundsException("Toa do nam ngoai pham vi ban do!");.
- Khối try...catch bên ngoài đón nhận ngoại lệ, in cảnh báo ra màn hình và giữ nguyên tọa độ cũ an toàn cho nhân vật.

TÌNH HUỐNG 3 8. "Hàm mẫu clampValue<T> trong CoreTemplates giải quyết tình huống máu nhân vật bị âm dưới 0 hoặc hồi máu vượt quá MaxHP ra sao?"
💡 Đáp án mẫu cho Vinh:

Dạ, hàm clampValue<T>(val, minVal, maxVal) có nhiệm vụ kẹp giá trị luôn nằm trong đoạn an toàn:
- Khi nhân vật bị trúng đòn sát thương chí mạng 9999, máu bị trừ xuống âm: gọi hp = CoreTemplates::clampValue(hp, 0, maxHp); sẽ ép máu về đúng 0, ngăn chặn hiện tượng máu bị số âm vô lý.
- Khi nhân vật uống liên tục 5 bình máu lớn, nếu máu vượt quá maxHp: hàm sẽ tự động cắt về đúng maxHp.
Đặc biệt vì là template, hàm này còn dùng được để kẹp tọa độ knockback của Boss Boar King không bị văng xuyên tường (kẹp trong khoảng từ ô 131 đến 163).

TÌNH HUỐNG 4 9. "Hàm mẫu lerpValue<T> giải quyết bài toán gì giúp hình ảnh chuyển động của nhân vật không bị giật cục giữa 2 ô lưới?"
💡 Đáp án mẫu cho Vinh:

Dạ, trong game theo lượt ô lưới, nhân vật nhảy từ ô x = 5 sang ô x = 6. Nếu vẽ ngay lập tức thì hình ảnh nhân vật sẽ bị dịch chuyển tức thời (dịch chuyển tức thời giật cục).
Hàm lerpValue<T>(start, end, t) cài đặt công thức **Nội suy tuyến tính (Linear Interpolation)**: start + (end - start) * t. Ở mỗi frame render, hàm sẽ tính toán tọa độ hiển thị trung gian nằm giữa ô cũ và ô mới theo hệ số thời gian thực t, giúp người chơi thấy nhân vật lướt đi vô cùng mượt mà trên màn hình 60 FPS.

TÌNH HUỐNG 5 10. "Tại sao toàn bộ các hàm khuôn mẫu (Function Template) trong file Templates.h bắt buộc phải viết phần thân trong file header (.h) mà không tách ra file .cpp?"
💡 Đáp án mẫu cho Vinh:

Dạ thưa thầy, vì khuôn mẫu hàm (Template) không phải là mã thực thi, mà chỉ là **bản thiết kế mẫu**. Trình biên dịch chỉ có thể sinh mã nhị phân khi nó nhìn thấy đồng thời cả hai thứ: định nghĩa của hàm mẫu và kiểu dữ liệu cụ thể được gọi (như int, float).
Nếu ta để định nghĩa hàm mẫu trong file Templates.cpp, khi các file khác (như CombatSystem.cpp, Player.cpp) include file Templates.h, trình biên dịch sẽ chỉ thấy phần khai báo chứ không thấy phần thân, dẫn tới không sinh được mã thực thi. Đến giai đoạn liên kết (Linking), Linker sẽ báo lỗi Undefined Reference. Do đó, mọi Template trong C++ bắt buộc phải được hiện thực trọn vẹn trong file header .h.
